Decision Models · Field Guide

Stop parsing prose. Start governing decisions.

A typed answer removes parser failure. It doesn't remove model error, policy, permissions, or the need to measure confidence against outcomes. Jev turns model output into a governed decision — gated, traced, and reviewed before anything acts.

The problem

A model can sound certain and still be wrong about its own shape.

Parse the wrong field out of generated text and you don't get an error — you get a plausible number in the wrong place. Stated confidence is no better: a model that says "92% confident" is making a claim about calibration, and that claim is frequently wrong until you measure it.

Calibration by confidence binillustrative
!
Shape is not truth.
A typed response guarantees you can read it. It does not guarantee the judgment inside it is correct — and a stated confidence is a claim to test, not a fact to trust.
Inside the one-pass decision engine

Cache the context once. Judge it four ways.

Where this shape earns its keep: high-volume workloads and real-time latency budgets — one cached context and four parallel judgments, not a slow multi-turn chain.

High-volumeReal-time
01 · DECLARE

Type the question first

Choose Choice, Score, or Noul before the model runs, so the shape of the answer can never be the thing that fails.

02 · EVALUATE

Run it in parallel

Independent judgments over one cached context — no invented causal link between them.

03 · CALIBRATE

Test the claim

Check stated confidence against your own fixtures, locally, before it drives anything.

Turn evidence into a route

Versioned rules decide what happens next. The model never executes its own verdict.

Vocabulary · System One

Three primitives. One decision geometry each.

PrimitiveWhat it capturesWhen to reach for it
ChoiceA closed set of named options, structurally guaranteed.Categorical decisions — a route, a label, a verdict — where every valid answer is enumerable in advance.
ScoreA bounded numeric judgment.Degree, not category — confidence, severity, distance to a threshold policy will apply.
NoulExplicit "insufficient evidence."When forcing a Choice or Score would manufacture false confidence.
≠
A typed answer is not a correct answer.
The structural guarantee stops at structure. Whether the judgment inside it is right is a separate question, checked by evaluators against evidence — not by the schema.
The provider-neutral decision layer

One typed layer. Policy above it, versioned separately.

Jev's typed primitives are the same whichever model answers them. What a Choice of "regression" actually triggers — a stage, a hold, an escalation — is application policy, so swapping the underlying model never means rewriting what the business does with its answers.

LAYER · JEV WIRE TYPES

Same whichever model answers

  • Choice / Score / Noul are structurally guaranteed
  • A model swap never breaks the schema
  • Cost of a wrong shape: zero

Where this runs today

Same engine. Two adapters, already shipping.

The Skill Loop and GTM Autoresearch already run this exact cycle — declare, evaluate, calibrate, apply policy, gate. They share bounded iteration, command execution, and evidence handling. What differs is only the adapter: the typed judgment shape, the evaluation rules, and the changes each is allowed to make.

ADAPTER · SKILL LOOP

Judges skill effectiveness

  • Choice{regression, no_drift} + a fixed-suite Score
  • Policy: candidate must strictly improve the score, never lose a passing check
  • Gate: approval verifies skill, suite, baseline, and evidence — then backs up the original
ADAPTER · GTM AUTORESEARCH

Judges config drift — and feeds the flywheel

  • A Score per static config dimension, Noul when one can't be assessed
  • Policy: candidates restricted to metadata edits only
  • Gate: no lost audit dimension, no new critical findings, no live import or publish
  • Same scored records ≥0.75 become fine-tuning data for client-specialized models; eval regression >0.05 auto-rolls the policy back
=
Jev isn't a third product.
It's the decision layer both already run on. In GTM Autoresearch the same Score that gates a config change also decides what becomes training data — one judgment, two consumers. Neither adapter's score alone proves live tracking or every skill is correct — that's what the human gate is still for.
Case study · GTM Autoresearch

One scored judgment, six jobs downstream.

GTM Autoresearch runs automated audits on live client GTM, Google Ads, and GA4 accounts, then turns every scored finding into training data for a client-specialized model — the same Score wire type Jev uses for calibration, doing double duty.

01 · LogEvery audit finding becomes a scored ExperimentRecord, 0–1, in SQLite.
02 · CollectGTM, Google Ads, and GA4 Admin API state versioned into one AccountState JSON.
03 · FilterScore ≥0.75 and de-duplicated at 0.92 cosine similarity survive to training data.
04 · Fine-tuneCloud (GPT-4o-mini) for most clients; local Llama 3.1 8B for zero-egress accounts.
05 · RouteEach client's fine-tuned model served by client ID, with RAG as fallback.
06 · FlywheelRetrains on 20 new examples; auto-rolls back if eval drifts more than 0.05.

From fixtures to auto-act

Auto-act is earned, not assumed.

01

Never auto-acts by default

Every candidate route is staged. A human approves before it reaches anyone, until fixture history says otherwise.

02

Targeted, not blind

Promotion criteria are explicit and versioned — not a vibe about how the model "seems" lately.

03

Model-version aware

Every trace records which model and runner produced the judgment, so a promotion never silently survives a model swap.

✓
General auto-act is not released.
A bounded check → repair → retest cycle with stop conditions is planned. Today, every route not yet cleared by fixtures ends in review.
