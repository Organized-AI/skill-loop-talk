The problem

Skills don't fail loudly. They get quietly worse.

A model update ships. The skill you built six months ago starts giving subtly wrong answers, and nothing tells you. You find out when a member complains, or you don't find out at all.

Building v1 gets all the attention.
Nobody plans for servicing it. The Skill Loop is the servicing plan: a baseline, a fixed test set, and a staged fix that waits for your approval.

Vocabulary

Three kinds of change. Only one is drift.

TermWhat happenedWhat it means
Effectiveness driftA check that passed now fails under the same versioned suite, scorer, and runner settings.Investigate and repeat. Model randomness can cause failures; one failure is evidence, not proof of cause.
Conditions changedThe suite or runner settings changed.The old baseline is no longer comparable. Establish a new one, reviewed separately.
GTM config driftThe container snapshot changed.Checks whether static audit dimensions got worse. It does not prove live conversion tracking broke.
≠
A changed file is not drift.
Drift is a previously passing check that now fails. That distinction keeps the loop honest about what it actually knows.
Shared foundation

One shared engine. Different QA checks.

Skill Loop and GTM Autoresearch share bounded iteration, command execution, and evidence handling. Their adapters define the inputs, the evaluation rules, and the changes each is allowed to make.

ADAPTER · SKILL LOOP

Checks output against task fixtures

  • Candidate must strictly improve the score
  • No previously passing check may be lost
  • Approval verifies skill, suite, baseline and evidence, then backs up the original
ADAPTER · GTM AUTORESEARCH

Checks six static config dimensions

  • Candidates restricted to metadata edits
  • No lost audit dimension, no new critical findings
  • No live import or publish

Why it's built this way

Evidence first. Humans approve.

01

Never auto-publishes

Every fix is staged as a diff. A human approves before it reaches anyone. Installing or testing never authorizes changing the active skill.

02

Targeted, not blind

Uses observed failures and cited QA sources to propose a revision, then tests it before review.

03

Model-version aware

Runs record the configured runner and test conditions. Drift flags an investigation; it does not prove the cause.

✓
If every check passes, keep the skill.
Don't invent a failure or weaken the original to manufacture an improvement. An all-pass result is a result.
Under the hood

Eight steps, three moves.

01 → Discover & understandRead accessible instructions and files. Record version and access limits.
02 → Test & explainRun explicit checks. Separate package findings, behavior, and human review.
03 ↻ Improve & rememberStage a revision, retest, review, optionally save history.
1
Connect
Declare scope. Installing grants no access to every skill.
2
Discover
Inventory the full package with fingerprints and gaps.
3
Define good
A versioned suite with stated coverage and QA source.
4
Run checks
Actual outputs, deterministic evaluators, per-check results.
5
Diagnose
Same checks, compatible conditions. Lost passes = drift.
6
Repair
Stage in a working copy. Inspect lost and gained passes.
7
Explore
Interactive QA artifact: cases, versions, findings.
8
Save
Optional D1 history, only after verified readback.

Auto Mode (bounded check → repair → retest with stop conditions) is planned, not released. Today, revisions are staged for review.
